# EscrowScout + ReceiptCheck — Telegraph Hackathon Season II

Two paired builds by **Nenzy Brown** (Dubai), founder of ProofReceipt and
PlateWallet. One registration, two tracks:

| Build | Track | What it is |
|---|---|---|
| **EscrowScout** | Apps & Agents — **Mission 01: Exchange** | An agent that vets a counterparty *before* an agent-to-agent payment, buying ranked intelligence through Telegraph and sealing every decision in a SHA-256 receipt. |
| **ReceiptCheck** | Miners / Providers | A callable Provider serving the `RECEIPT_INTEGRITY_VERIFY` intent: given a delivery receipt and the delivered bytes, it returns MATCH / MISMATCH / INVALID with a signed evidence bundle. It is the production verification logic behind [ProofReceipt](https://proofreceipt.netlify.app) (live) exposed as graded intelligence. |

## EscrowScout — trust, but verify, before the agent pays

For a proposed payment (counterparty wallet + escrow contract + amount),
EscrowScout:

1. **Buys intelligence through Telegraph** — one paid request per Intent:
   `SANCTIONS_SCREENING_MATCH`, `ONCHAIN_METRIC_VERIFY`,
   `SMART_CONTRACT_AUDIT`. Each answer names the serving miner, its rank,
   the price, and the protocol receipt.
2. **Inspects the escrow contract on-chain** (live RPC reads): who can
   release the funds, whether a refund path exists, admin/owner keys, and
   upgradeability (EIP-1967 proxy slots), plus a structured read of
   buyer/seller/arbiter/deadline when the contract exposes them.
3. **Decides and seals the decision**: deterministic verdict rules
   (sanctions match or a critical audit finding are hard stops) produce
   `PROCEED` / `PROCEED_WITH_CAUTION` / `DO_NOT_PAY` with a full deduction
   trail, and the whole evaluation report is sealed in a **ProofReceipt-format
   SHA-256 receipt** — the same canonical format as the live ProofReceipt
   app, byte-identical (a cross-check vector generated by the app's own
   JavaScript is pinned in the tests), so any decision can be re-audited
   byte-for-byte later.

## ReceiptCheck — receipt integrity as an Intent

`POST /v1/receipt-check` with a ProofReceipt receipt JSON and the delivered
bytes (text or base64 file). It recomputes the canonical SHA-256 twice —
once over the deliverable, once over the receipt fields — and answers:

- **MATCH** — both recomputations agree with the receipt;
- **MISMATCH** — well-formed receipt, but the deliverable was altered, or
  the receipt fields were altered after sealing (the bundle says which);
- **INVALID** — the payload is not a well-formed receipt at all.

Every answer is a signed evidence bundle (EIP-191 signature by the provider
wallet over the bundle hash), so the verdict itself is verifiable by anyone.

## Quickstart

Prerequisites: Python 3.11+ with `web3` and `eth-account` (everything else
is stdlib), Foundry only if you redeploy the sample escrow. No installs are
needed for the test suite or the demo.

```bash
cd telegraph-build

# 1. Run the tests (20 tests; the live-RPC inspector test is opt-in)
python3 -m unittest discover -s tests
LIVE_RPC_TESTS=1 python3 -m unittest discover -s tests   # adds live Base Sepolia reads

# 2. ReceiptCheck provider (Miners track)
python3 -m receiptcheck.core        # self-test log: 4 cases, all correct, ~10–30 ms each
python3 -m receiptcheck.server      # serves http://127.0.0.1:8791  (GET /health, POST /v1/receipt-check)

# 3. EscrowScout evaluations (Apps & Agents track)
python3 -m escrowscout.scout --wallet 0x71C7656EC7ab88b098defB751B7401B5f6d8976F \
    --escrow 0x6c4EE22087B8c971027cB61fD35e8EB6bD84CFDB --amount 150 --out /tmp/out

# 4. The whole flow in one command (starts the provider, runs 3 evaluations,
#    then has ReceiptCheck verify EscrowScout's own receipt)
python3 scripts/run_demo.py         # transcript -> examples/demo-output.txt
```

## Sample escrow (testnet)

`contracts/src/SampleEscrow.sol` is a deliberately simple escrow used as the
inspection target: release needs the buyer or the arbiter, the buyer can
refund after the deadline, no admin key, no upgradeability. It is deployed
and funded on **Base Sepolia**:

- Address: `0x6c4EE22087B8c971027cB61fD35e8EB6bD84CFDB`
- Deploy tx: `0x53f23929bd7aaf178ab5597ff0486b02c729e7473eda84c5ee07b07887238a02`
- Explorer: https://sepolia.basescan.org/address/0x6c4EE22087B8c971027cB61fD35e8EB6bD84CFDB
- Redeploy: `scripts/deploy_sample_escrow.sh` (needs a faucet-funded Base
  Sepolia key in `DEPLOYER_PRIVATE_KEY`; see `deployments.json`).

## Demo flow (for the 2–5 minute video)

1. **Problem** (0:00) — an agent is about to pay a counterparty 150 USDC.
   Paying the wrong wallet is irreversible; a receipt that doesn't match the
   delivered work is worthless.
2. **Telegraph request** (0:30) — run the clean EscrowScout evaluation:
   three paid Intent requests, miner + rank + price + protocol receipt for
   each; total intelligence cost 0.024 USDC.
3. **Intelligence + inspection evidence** (1:15) — show the live Base
   Sepolia inspection of the SampleEscrow (buyer/arbiter release, refund
   after deadline) and the verdict: PROCEED, 100/100. Show the evaluation
   receipt (SHA-256).
4. **Failure cases** (2:00) — the new-wallet evaluation
   (PROCEED_WITH_CAUTION, 60/100) and the sanctions-matched wallet
   (DO_NOT_PAY, hard stop). Then ReceiptCheck on the clean evaluation:
   genuine report → MATCH; change one number in the report → MISMATCH.
5. **How to try it** (2:45) — `python3 scripts/run_demo.py`, tests, and the
   ReceiptCheck endpoint; point at `INTEGRATION_NOTES.md` for exactly what
   is live, what is fixture-mode, and what remains.

## Network status — read this before scoring the integration

Honest labelling, per the Season II rules:

- **Live today:** the ReceiptCheck endpoint and its signed bundles; all
  ProofReceipt receipt creation/verification; the SampleEscrow deployment
  and EscrowScout's on-chain inspection of it (real Base Sepolia reads);
  the full local demo and test suite.
- **Fixture mode:** EscrowScout's Telegraph purchases in the demo run
  against deterministic local miners whose responses use the network's
  documented answer shapes. They are labelled `mode: "fixture"` in every
  evaluation report. No fixture output is presented as live network traffic.
- **Live mode is implemented, not yet executed:** `X402Transport` in
  `escrowscout/telegraph_client.py` performs the documented purchase flow
  (request → HTTP 402 → signed EIP-3009 USDC authorization → answer +
  protocol receipt). It needs two things listed in `INTEGRATION_NOTES.md`:
  the network API base assigned to builders, and an agent wallet funded
  with Base Sepolia test USDC. That is the Nov 14 integration milestone
  work, and it is a configuration step, not a code rewrite.
- ReceiptCheck's network registration is prepared (`receiptcheck/miner.yaml`
  — Telegraph's one-config-file plug-in model); pointing the node software
  at it with the provider wallet is the remaining step, also tracked in
  `INTEGRATION_NOTES.md`.
